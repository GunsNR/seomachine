# Hosted PostgreSQL validation

Status: **executed against Railway PostgreSQL 16.15 on 2026-08-25 — passed** · last reviewed 2026-08-25

This is the procedure that closes Phase 2's last open acceptance criterion:
proving the migration works against a real hosted database with
production-shaped data, and proving a backup can actually be restored.

Steps 1–9 are automated and run on every CI push against a disposable
PostgreSQL 16 service, so the procedure itself is exercised continuously. On
2026-08-25 the same procedure also ran against a **hosted** endpoint — Railway
PostgreSQL 16.15, `iad`, private-network-only — and passed: migrations applied
to the provisioned database with zero drift, and a `pg_dump`/`pg_restore` round
trip preserved every integrity field. Evidence, including the TLS and latency
findings and an explicit list of what the run still does not prove, is in
`evidence/2026-08-25-hosted-postgres-validation-railway.md`.

An earlier attempt the same day reached no database at all, blocked by egress
policy; it is kept in `evidence/2026-08-25-hosted-postgres-provisioning-attempt.md`
and is superseded by the run above.

**What a hosted pass still does not settle** is §2 below: pooler behaviour,
connection limits, the provider's own snapshot/PITR path, and production-*sized*
data. Those remain open, and a green run here may not be read as covering them.

---

## 0. Before you start

You need:

- A hosted PostgreSQL instance you can create and drop databases on.
- Its **direct** (non-pooled) connection string.
- `pg_dump` and `pg_restore` at a major version **≥** the server's.

You do **not** need, and must not use:

- Real customer data. The dataset is synthetic and generated by the script.
- Production credentials in any file. Pass connection strings by environment
  variable only.

### One constraint that will bite you

The generated migrations qualify every object as `"public"."Table"` — Prisma
bakes the schema name in at generation time. **The target database must use the
`public` schema.** A database configured around a different default schema will
fail with `relation "User" already exists` or create objects somewhere you did
not expect.

### The two connection strings

`DATABASE_URL` is runtime traffic and may be pooled. `DIRECT_URL` is for
migrations, `pg_dump`, `pg_restore` and administration, and must **not** be
pooled: a transaction-mode pooler multiplexes statements across backends, which
breaks advisory locks, temp tables, prepared statements and `SET` — all of which
migrations use. The failure looks intermittent and random, which is the worst
kind.

Prisma **requires** `DIRECT_URL` once the schema declares it. Leaving it unset is
a hard error, not a fallback to `DATABASE_URL`. Where a provider has no separate
direct endpoint, set both to the same value.

## 1. Run the automated rehearsal

Steps 1 through 9 of the required procedure are one command:

```bash
cd supertool
export DIRECT_URL="postgresql://USER:PASSWORD@HOST:5432/DATABASE"
export DATABASE_URL="$DIRECT_URL"     # or the pooled endpoint
export PGPASSWORD="PASSWORD"          # pg_dump/pg_restore read this

npm run db:rehearse -- --report ../rehearsal-$(date +%Y%m%d-%H%M).json
```

It creates its own disposable source and restore databases, and drops both when
it finishes. Pass `--keep` to leave them for inspection.

### What it does, mapped to the required steps

| # | Requirement | How it is done |
| --- | --- | --- |
| 1 | Sanitized, production-shaped dataset, no client PII | Generated in-process: two tenants, four projects, eight runs, twenty-four observations, jobs, sessions and scoped API keys. Nothing is read from any real source, so PII cannot enter. |
| 2 | `migrate deploy` to an empty hosted database | Creates an empty database, then runs `prisma migrate deploy` — the same command production uses. |
| 3 | Confirm zero schema drift | `prisma migrate diff --exit-code` plus `prisma migrate status`. Non-zero exit fails the rehearsal. |
| 4 | Import the representative dataset | Written through the Prisma client, so every constraint is exercised on the way in. |
| 5 | Verify tenants, runs, observations, jobs, sessions, API-key scopes | See the integrity checks below. |
| 6 | Back up with `pg_dump` | Custom format, `--no-owner --no-acl`, so the dump restores under a different role. |
| 7 | Restore into an isolated database | A second database created for the purpose. The source is never touched. |
| 8 | Re-run integrity checks | The same function, against the restored copy. |
| 9 | Record timings, failures, provider, version, migration SHA, evidence | `--report` writes JSON with per-step timings, the PostgreSQL version string, the Prisma version, the git SHA, the migration list, and both integrity snapshots. |

### The integrity checks

Chosen because each one catches a specific way a restore can silently lose
something that matters:

| Check | What it would catch |
| --- | --- |
| Row counts for organisations, projects, runs, observations, jobs, sessions, API keys | Wholesale data loss |
| `orphanedProjects`, `orphanedObservations` | A restore that dropped or reordered foreign keys, breaking tenant scoping |
| `observedCount` / `failedCount` / `unavailableCount` separately | A restore that kept only successful rows. Coverage is computed from failed and unavailable observations, so losing them **silently inflates every published rate** — the Gate 1 invariant most easily destroyed by a bad restore |
| `daysWithMultipleRuns` | Loss of run identity. Two runs on one UTC day must stay two runs (Gate 1) |
| `keysWithoutScopes` | Scope columns dropped, re-granting every key full access |
| `idempotencyConstraintEnforced` | A restore that recreated tables without their unique constraints — the failure that makes retries double-count |

The comparison is field by field. **Any** difference between source and restored
fails the rehearsal.

There is also a guard against the rehearsal passing vacuously: it asserts the
dataset actually loaded (≥ 2 tenants, ≥ 1 observation, ≥ 1 same-day run pair,
constraint enforced). Without it, comparing two empty databases would pass.

## 2. What the automated rehearsal does *not* prove

Run it against a hosted target and it still tells you nothing about:

- **Pooler behaviour.** Whether your `DATABASE_URL` pooler handles the app's
  concurrency, and whether anything accidentally routes a migration through it.
- **Connection limits.** The rehearsal opens a handful of connections. Your plan
  may cap far lower than the app needs under load.
- **Latency.** Every timing in the report is against whatever you pointed it at.
  A local run says nothing about a remote one.
- **The provider's own backup and restore.** `pg_dump`/`pg_restore` is the
  portable path. Provider snapshots, PITR and branch-restore are separate
  mechanisms with separate failure modes, and each needs its own rehearsal.
- **Real data volume.** Twenty-four observations is production-*shaped*, not
  production-*sized*. A migration that locks a table for an hour on ten million
  rows completes instantly here.

Record these as open after any hosted run. Do not let a green rehearsal be read
as "validated at scale".

## 3. Manual steps that remain

After the automated rehearsal passes against the hosted target:

1. **Load-shaped timing.** Generate a dataset at the scale you expect within
   twelve months and re-run. Record how long `migrate deploy` holds locks.
2. **Pooler routing.** Confirm the app reaches the pooled endpoint and
   migrations do not. Point `DATABASE_URL` at the pooler, `DIRECT_URL` at the
   direct endpoint, run the app, and check the provider's connection view.
3. **Provider backup.** Take a provider-native snapshot, restore it into a fresh
   branch or instance, and run the integrity checks against it:
   ```bash
   DIRECT_URL="<restored-instance-url>" npm run db:rehearse -- --keep
   ```
   (The rehearsal will create its own databases; for a restored-snapshot check
   you want the integrity portion only — run it against a copy, never against
   the live instance.)
4. **Failure injection.** Kill the migration mid-run and confirm the recorded
   state is coherent and re-runnable. `npm run db:recovery-drill` covers the
   constraint-failure case against a disposable instance; what a hosted run adds
   is the process- and connection-death cases, which need a real network path to
   interrupt.

## 4. Rollback and forward-fix criteria

Decide **before** applying anything to a database holding real data.

### Forward-fix — the default

Applies when the migration succeeded but the application is unhappy, and the
change was **additive** (new table, new nullable column, new index).

- Roll back the *application*, leave the schema. An unused column is harmless.
- Write a new migration correcting the state.
- Never edit an applied migration file. It has already run somewhere.

### Restore — the escape hatch

Applies when the migration **destroyed or transformed data**: a dropped column,
a narrowed type, a backfill that wrote wrong values.

- Restore from the backup taken immediately before the migration. There is no
  cleverer option, which is why taking that backup is not optional.
- Expect to lose everything written between the backup and the restore. Know
  that window before you start.

### Abort before starting

Do not proceed if any of these is true:

- No backup was taken in the last few minutes.
- The backup has never been restored successfully (run the rehearsal first).
- `prisma migrate status` reports drift, or a migration applied outside this
  history.
- The migration drops or narrows a column and no forward-fix exists.
- You cannot state, in one sentence, how you would undo it.

### The decision, as a table

| Situation | Action |
| --- | --- |
| Additive migration, app broken | Roll back the app, forward-fix |
| Additive migration, migration failed partway | Re-run `migrate deploy` — it resumes |
| Destructive migration, wrong result | Restore from backup |
| Drift detected before applying | Stop. Reconcile the history first |
| Drift detected after applying | Restore, then reconcile |
| Rehearsal never run against this provider | Do not apply anything |
| Migration failed, `migrate deploy` now refuses (P3009) | Resolve the history — see below |

### Recovering a wedged pipeline

Rehearsed on 2026-08-31 against disposable PostgreSQL 16, and re-executed by CI
on every push: `npm run db:recovery-drill`. Full account in
`evidence/2026-08-31-migration-recovery-drill.md`; the operator procedure is
`operations-runbook.md` §2.

The finding worth carrying into a hosted run: on PostgreSQL a migration that
fails partway leaves **the schema untouched and the history damaged**. DDL is
transactional and Prisma sends a migration as one implicit transaction, so there
is usually no half-applied schema to clean up — but `_prisma_migrations` keeps a
failed row and every later `migrate deploy` refuses with P3009 until
`migrate resolve --rolled-back` clears it. Look at the history before you go
looking for residual DDL.

This does not hold for statements PostgreSQL cannot run inside a transaction —
`CREATE INDEX CONCURRENTLY` foremost among them. A migration containing one of
those can genuinely leave a half-applied schema, and that case is **not**
rehearsed.

## 5. Evidence to keep

Every hosted run should leave:

- The `--report` JSON: timings, versions, migration SHA, both integrity
  snapshots, per-step results.
- The provider and region.
- The exact `pg_dump` and server version strings.
- Anything that failed, and what was changed in response.

Store it alongside the release it validates. A rehearsal whose evidence was not
kept is a rehearsal nobody can point at later.

---

## 6. In CI

`npm run db:rehearse` runs on every push against the disposable `postgres:16`
service, so the whole procedure is executed continuously rather than only
documented. What CI proves is that the migrations apply cleanly, produce no
drift, and survive a dump/restore round-trip with integrity intact.

What CI does **not** prove is anything in §2. Those need a hosted target and a
person.
